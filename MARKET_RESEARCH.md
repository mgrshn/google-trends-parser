# Google Trends Mass Scraping: варианты реализации

Целевой объём: **1 млн ключевиков в день**

---

## 1. Официальный Google Trends API

**Не существует** для публичного использования. Google не предоставляет официального API с документацией и квотами для массового парсинга трендов.

Есть внутренний неофициальный API (используется самим сайтом trends.google.com):
- `GET /trends/api/explore` — получение токенов
- `GET /trends/api/widgetdata/multiline` — получение временного ряда

Именно его используют все решения ниже — и pytrends, и наше, и большинство провайдеров.

**Риск:** Google может изменить API без предупреждения в любой момент.

## 3. Pytrends (open source)

Неофициальная Python-библиотека, обёртка над тем же внутренним API Google.
Использует стандартный `requests` без TLS impersonation.

```python
from pytrends.request import TrendReq
pytrends = TrendReq()
pytrends.build_payload(["bitcoin"], timeframe="today 12-m")
df = pytrends.interest_over_time()
```

### Результаты тестирования (50 ключевиков)

| Условие | Success rate | Avg/запрос |
|---|---|---|
| Без прокси (домашний/VPN IP) | **100%** | **0.8s** |
| С датацентровыми прокси | **30%** | 1.1s |

Без прокси работает отлично — быстрее нашего решения (нет warmup, нет curl_cffi overhead).  
С прокси — 30% success: стандартный `requests` не подделывает TLS fingerprint, Google легко детектирует бота через прокси.

**+** Бесплатно  
**+** Быстрый старт, минимум кода  
**+** 0.8s/запрос без прокси — быстрее curl_cffi  
**−** Без TLS impersonation — с прокси success rate 30% vs 93% у нашего решения  
**−** Несовместим с urllib3 2.0+ при использовании прокси с retries (баг в библиотеке)  
**−** Поддерживается комьюнити: при изменении API Google чинится медленно (дни/недели)  
**−** Нет встроенного proxy pool, очереди, кэша  
**−** Не подходит для продакшна при любом серьёзном объёме

## 4. Своё решение

Архитектура: `FastAPI → Redis Queue → Worker Pool → PostgreSQL`  
Скрейпер: `curl_cffi` с `impersonate=chrome124` (TLS fingerprint Chrome)  
Кэш: per-timeframe TTL, данные отдаются из БД без повторного запроса к Google  

**Общие + для всех вариантов своего решения:**  
+ В 4–20x дешевле любого managed-провайдера при 1М/день  
+ Полный контроль над данными и логикой  
+ Кэш-first: повторные запросы бесплатны  
+ Горизонтальное масштабирование воркеров без изменений архитектуры  

**Общие − для всех вариантов своего решения:**  
− Уязвимо к изменениям внутреннего API Google (как и pytrends)  
− Требует инженерного ресурса на поддержку  
− При смене API Google нужно чинить самостоятельно

### 4а. Датацентровые прокси

Стоимость при 1М/день: **$600–2 400/мес**  
Цена/GB: $0.5–2 | Success rate: ~25%

**+** Дёшево на старте  
**+** Легко купить у любого провайдера  
**−** Google знает диапазоны датацентровых IP (AWS, DO, Hetzner)  
**−** Rate limit: 2–3 запроса на IP → 429, cooldown 1–2 часа  
**−** Из-за низкого success rate нужно в 4x больше запросов — реальная стоимость растёт  
**−** Требует огромного пула IP для 1М/день  

---

### 4б. Резидентские прокси ✅ Рекомендуемый вариант

Стоимость при 1М/день: **$500–2 600/мес**  
Цена/GB: $1.5–8 | Success rate: ~90% (оценочно, не тестировалось)  
Провайдеры: Smartproxy/Decodo, BrightData, IPRoyal, Oxylabs

> ⚠️ **Не тестировалось.** Success rate и поведение с резидентскими прокси — оценка на основе индустриальных данных. Реальные показатели будут уточнены при получении прокси.

**+** Реальные домашние IP — Google видит обычных пользователей  
**+** Высокий success rate, на порядок меньше банов чем с датацентровыми  
**+** Наша архитектура работает без изменений — меняется только proxies.txt  
**+** Сопоставимо по цене с датацентровыми при учёте реального throughput  
**−** Дороже датацентровых по цене/GB  
**−** Скорость запроса чуть выше (~4–6s vs ~2–3s)  

---

### 4в. Мобильные прокси

Стоимость при 1М/день: **$4 300–7 700/мес**  
Цена/GB: $14–25 | Success rate: ~97%  
Провайдеры: BrightData Mobile, Smartproxy Mobile

**+** IP мобильных операторов — Google банит крайне редко  
**+** Максимальный success rate из всех вариантов  
**+** Один IP может обрабатывать больше запросов без бана  
**−** В 3–5x дороже резидентских  
**−** Оправдано только если каждый запрос критичен и нельзя терять на retry
